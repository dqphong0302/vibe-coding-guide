1. Kiến trúc nền tảng và mô hình suy luận của Codex

OpenAI Codex không chỉ là một chatbot lập trình thông thường. Nền tảng của nó là các mô hình lý luận chuyên biệt (Reasoning Models), đặc biệt là dòng o3, o3-mini và GPT-4o, được tối ưu hóa cho bài toán lập trình đa bước có điều kiện ràng buộc phức tạp.

Điểm khác biệt cốt lõi so với các chatbot thông thường là Codex hoạt động theo mô hình tác nhân thực thi (Execution Agent): nó không chỉ sinh văn bản mô tả giải pháp mà còn thực sự chạy các lệnh trong môi trường sandbox, quan sát đầu ra, phân tích kết quả và tự điều chỉnh hướng đi cho đến khi đạt mục tiêu. Cơ chế này gọi là vòng lặp Observe-Plan-Execute-Verify (OPEV):

  1. Observe (Quan sát): Codex đọc toàn bộ mã nguồn trong thư mục dự án, phân tích cấu trúc file và nội dung AGENTS.md để nắm bối cảnh.
  2. Plan (Lên kế hoạch): Codex tự phân rã yêu cầu thành các nhiệm vụ nhỏ có thứ tự thực hiện rõ ràng và dự đoán các rủi ro kỹ thuật.
  3. Execute (Thực thi): Codex viết mã, chạy lệnh trong Sandbox, xem kết quả và tiếp tục điều chỉnh cho đến khi đạt kết quả mong muốn.
  4. Verify (Xác minh): Codex chạy các bộ test (pytest, jest) để tự kiểm tra tính đúng đắn của mã nguồn vừa tạo trước khi trình kết quả cho người dùng.

2. Terminal Sandbox: Pháo đài an toàn cho tự động hóa

Đây là tính năng phân biệt Codex khỏi tất cả các AI khác. Mọi lệnh terminal mà Codex cần thực thi đều chạy trong một môi trường container cô lập hoàn toàn, không có quyền truy cập vào file system thật của bạn nếu không được cấp phép rõ ràng.

Codex hỗ trợ 3 chế độ phê duyệt (Approval Mode) khác nhau:

Chế độCờ lệnhHành viDùng khi nào
Tự động hoàn toàn--approval-mode autoTự chạy mọi lệnh mà không hỏiMôi trường CI/CD đáng tin cậy
Thủ công (khuyến nghị)--approval-mode manualHỏi xác nhận trước mỗi lệnhDự án thực tế, code quan trọng
Chỉ đọc--approval-mode suggestChỉ đề xuất, không thực thiRà soát, phân tích bảo mật
CÁC LỆNH CODEX CLI THIẾT YẾU
# Cài đặt Codex CLI toàn cục
npm install -g @openai/codex

# Khởi động phiên làm việc chế độ thủ công (an toàn nhất)
codex --approval-mode manual

# Yêu cầu Codex phân tích bảo mật, không sửa file
codex --approval-mode suggest "Rà soát toàn bộ thư mục /api và liệt kê các lỗ hổng SQL Injection tiềm năng"

# Yêu cầu Codex cài dependencies và chạy test
codex "Cài đặt jest, tạo file test cơ bản cho module auth.js và chạy npm test"

# Yêu cầu với giới hạn thư mục cụ thể
codex --workspace ./backend "Refactor hàm validateUser để hỗ trợ OAuth2"

3. Phân cấp quy tắc AGENTS.md: Hệ thống điều lệ của dự án

File AGENTS.md là "hiến pháp" của dự án dành cho Codex. Hệ thống đọc file này theo cấu trúc phân cấp thư mục: file ở thư mục gốc áp dụng cho toàn dự án, file ở thư mục con sẽ kế thừa và ghi đè cho phạm vi đó. Đây là một ưu điểm mạnh hơn file GEMINI.md của Antigravity vì cho phép quy tắc chi tiết theo từng module.

CẤU TRÚC AGENTS.md TOÀN DIỆN CHO DỰ ÁN
# ======================================================================
# AGENTS.md - Điều lệ tự động hóa toàn dự án (ROOT LEVEL)
# Phiên bản: 2.0 | Áp dụng cho: Google Antigravity, OpenAI Codex, Claude
# ======================================================================

## 1. NGUYÊN TẮC BẤT BIẾN (Không bao giờ vi phạm)
- **Không xóa mã nguồn cũ** nếu chưa có sự xác nhận rõ ràng từ người dùng.
- **Không tự ý tạo thêm tính năng** nằm ngoài phạm vi v1 trong SPEC.md.
- **Không hardcode** API Key, password, connection string vào bất kỳ file nào.
- **Không xóa file SPEC.md, AGENTS.md** hoặc bất kỳ tài liệu dự án nào.

## 2. NGÔN NGỮ VÀ TECH STACK
- Frontend: HTML5 ngữ nghĩa, Vanilla CSS/JavaScript (không dùng jQuery).
- Backend: Node.js (Express) hoặc Python (FastAPI) theo SPEC.md.
- Database: SQLite (phát triển cục bộ), PostgreSQL (production).
- Deployment: Vercel (frontend), Railway (backend).

## 3. QUY ƯỚC ĐẶT TÊN MÃ NGUỒN
- Hàm JavaScript/Python: camelCase hoặc snake_case tùy ngôn ngữ.
- Hằng số: UPPER_SNAKE_CASE (ví dụ: MAX_RETRY_COUNT).
- Tên file: lowercase-kebab-case (ví dụ: user-auth.js, api-gateway.py).
- Database table/column: snake_case (ví dụ: user_profiles, created_at).

## 4. PHONG CÁCH PHẢN HỒI
- Sau mỗi lần thực thi, tóm tắt: (1) Những file đã thay đổi, (2) Lý do thay đổi, (3) Bước tiếp theo đề xuất.
- Khi gặp điểm không rõ trong yêu cầu, HỎI TRƯỚC khi làm.
- Luôn viết comment tiếng Việt cho logic phức tạp.

## 5. TEST VÀ ĐẢM BẢO CHẤT LƯỢNG
- Viết unit test cho mọi hàm xử lý nghiệp vụ cốt lõi.
- Sau khi sửa bug, chạy `npm test` hoặc `pytest` để kiểm tra hồi quy.
- Báo cáo bao phủ test (Coverage) nếu được yêu cầu.

4. Session Tree & Branching: Thử nghiệm song song các giải pháp

Đây là tính năng độc quyền của Codex Desktop không có trên bất kỳ AI coding tool nào khác. Session Tree cho phép bạn rẽ nhánh phiên làm việc như Git — từ một điểm gốc, bạn có thể thử nghiệm nhiều hướng tiếp cận song song mà không làm ảnh hưởng lẫn nhau.

VÍ DỤ THỰC TẾ — PHÂN TÍCH LỰA CHỌN KIẾN TRÚC CSDL:
Bạn đang phân vân giữa SQLite và PostgreSQL cho hệ thống quản lý đơn hàng 10,000 bản ghi/ngày.

Nhánh A (SQLite): Tạo từ commit gốc → Codex xây dựng phiên bản SQLite → Chạy benchmark 10,000 bản ghi → Đo thời gian query: 45ms trung bình.
Nhánh B (PostgreSQL): Tạo từ cùng commit gốc → Codex xây dựng phiên bản PostgreSQL + index → Chạy cùng benchmark → Thời gian query: 8ms với full-text search.

Kết quả: Bạn so sánh trực quan trên Session Tree và chọn nhánh B. Codex merge nhánh B vào nhánh chính chỉ với một cú click.

Quy trình sử dụng Session Branching chuyên nghiệp:

  1. Commit điểm khởi đầu: Trước khi rẽ nhánh, đảm bảo codebase ổn định và đã được kiểm thử cơ bản.
  2. Tạo nhánh thử nghiệm: Click "Branch Session" trên giao diện Codex Desktop hoặc dùng lệnh codex branch "Thử kiến trúc microservices".
  3. Thử nghiệm độc lập: Mỗi nhánh hoạt động hoàn toàn độc lập — bao gồm file system và terminal sandbox riêng.
  4. So sánh và quyết định: Xem diff giữa các nhánh, kiểm tra kết quả test và chọn nhánh tốt nhất.
  5. Merge hoặc Abandon: Apply nhánh được chọn vào project thật, các nhánh thất bại được xóa sạch không để lại vết.

5. Visual Diff Reviewer: Quyền kiểm soát tối cao của lập trình viên

Mọi thay đổi Codex đề xuất đều phải đi qua màn hình Visual Diff trước khi được ghi vào file thật. Đây là cơ chế bảo vệ quan trọng nhất, ngăn chặn trường hợp AI tự ý thay đổi logic quan trọng mà bạn không nhận ra.

Cách đọc màn hình Visual Diff hiệu quả:

  • Dòng màu xanh lá (+): Mã mới được thêm vào — luôn đọc kỹ để đảm bảo logic đúng với ý định.
  • Dòng màu đỏ (-): Mã cũ bị xóa — kiểm tra xem có logic nghiệp vụ quan trọng nào đang bị xóa không.
  • Dòng xám (context): Mã không thay đổi, hiển thị để bạn hiểu ngữ cảnh xung quanh.
  • Header @@ -10,7 +10,15 @@: Cho biết thay đổi bắt đầu từ dòng 10, cũ có 7 dòng, mới có 15 dòng.
THÓI QUEN CHUYÊN NGHIỆP KHI REVIEW DIFF:
Trước khi bấm "Apply Changes", hãy kiểm tra 3 điều: (1) Có dòng xóa nào chứa logic xử lý lỗi quan trọng không? (2) Có dòng thêm nào giới thiệu dependency mới không cần thiết không? (3) Có bất kỳ thông tin nhạy cảm nào (key, password, token) xuất hiện trong diff không? Nếu có bất kỳ dấu hiệu đáng ngờ nào, hãy chọn "Request Changes" thay vì "Apply".

Codex CLI không chỉ dùng cho phát triển thủ công — nó có thể chạy tự động trong pipeline CI/CD như một bước tự động hóa thông minh:
